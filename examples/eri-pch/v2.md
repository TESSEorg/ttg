# eri-pch_v2 — single TTG dataflow graph with feedback edge

Same algorithm and numerics as `eri-pch_v1`, but the **outer iteration loop
is folded into TTG**. The decomposition runs as a single connected graph
that produces its own next-iteration trigger.

## TTG topology

```
                                            ┌──────────────────────────────┐
   invoke() ─▶ drive_diag ─▶ compute_diag ─▶│ diag_barrier (streaming, x nsp)│
                                            └────────────┬─────────────────┘
                                                         │ Edge<int,void> e_seed_iter
                                                         ▼
                  Edge<int,void>           ╔═══════════════════════════════╗
                  e_loop_iter (feedback) ─▶║         iter_dispatch         ║
                  ┌─────────────────────── ║   in0 = fuse(e_seed_iter,     ║
                  │                        ║              e_loop_iter)     ║
                  │                        ║   out0: continue              ║
                  │                        ║   out1: terminate             ║
                  │                        ╚═══════════╤═══════════╤═══════╝
                  │                                    │           │
                  │             Edge<MultiIndex<2>,    │           │ Edge<int,void>
                  │              size_t> e_pivot_in    │           ▼
                  │                                    ▼     ┌───────────┐
                  │                          ┌──────────────┐│ terminate │
                  │                          │ compute_slab ││           │
                  │                          └──────┬───────┘└───────────┘
                  │                                 │  Edge<int, PivotSlabs>
                  │                                 │  e_pivot_collect
                  │                                 ▼
                  │                       ┌──────────────────────────────┐
                  │                       │ gather_pivot (streaming x nsp)│
                  │                       │  assemble Q from slabs;       │
                  │                       │  run sub-decomp;              │
                  │                       │  emit iter+1                  │
                  └─────────────────────────────  out0  ─────────┘
```

Two streaming reducers, both with `set_static_argstream_size(nsp)`:

- **`diag_barrier`** — `Edge<int,int>` with sum reducer. The integer payload
  is unused; what matters is that exactly `nshell_pairs` arrivals at key=0
  are required before it fires. On firing, prescreens `d[]` and emits
  `iter=0` onto the seed edge.

- **`gather_pivot`** — `Edge<int, std::vector<PivotSlab>>` with concat
  reducer. Each `compute_slab` emits a single-element `PivotSlabs`; after
  `nshell_pairs` arrivals at the iteration's key, the reducer holds all
  slabs for that iteration and the task fires.

The feedback edge is `e_loop_iter`; iter_dispatch's input terminal uses
`fuse(e_seed_iter, e_loop_iter)` (the `Everything5` self-loop pattern from
`tests/test.cc`).

## Pure dataflow vs. metadata

What flows on edges (pure dataflow):

- `pivot_sp_idx` (the iteration's pivot shell pair) on `e_pivot_in`, set
  by `iter_dispatch` and read by every `compute_slab`.
- `PivotSlab` (one shell pair's row block of `Q`) on `e_pivot_collect`.
  Carries `sp_idx`, `pivot_sp_idx`, `pair_begin`, `npairs`, `W`, and the
  `npairs * W` doubles. Has a templated `serialize` (madness one-arg and
  boost two-arg) — required because parsec instantiates
  `default_data_descriptor<PivotSlab>` even in shared memory.

What stays as metadata (shared by reference into lambdas):

- `D`              — basis layout, read-only after build.
- `pool`           — per-thread libint2 engines (internally locked).
- `d[]`            — running diagonals. Written by `compute_diag` (disjoint
                      slices) and by `gather_pivot` (sequential, after
                      streaming barrier). Never read concurrently.
- `L[]`            — finished Cholesky vectors. Only `gather_pivot` writes.
- `total_shellpair_recomputes` — a counter only iter_dispatch updates.

The serialization invariant: `gather_pivot` for iteration N runs to
completion (including all sub-decomp updates of `d[]` and appends to `L[]`)
before emitting `iter+1`, so iter_dispatch for N+1 always sees consistent
metadata. No locking needed.

## What's still sequential

The **sub-decomposition inside `gather_pivot`** is still a serial loop:

```text
while (sub_pivot in pivot_sp with d[sub] > X_max/1000):
    apply_cholesky_update(sub_pivot)
```

Each call to `apply_cholesky_update` reads previously appended `L^K` vectors
and writes a new one. The read-after-write chain across sub-pivots is tight,
so there isn't much to gain from sub-task-level parallelism here. The
*per-row* scatter inside one update is parallelizable, however, and is the
natural target for a future v3.

## Strengths

- One graph, one fence — drive `t_diag_drive->invoke()` and a single
  `ttg::fence()` drains the whole decomposition.
- Iterations can in principle overlap with their predecessors at the
  granularity of the per-iter integral compute and reduce; in this run the
  feedback dependence forces strict ordering, but the runtime no longer
  pays a host-side fence between iterations.
- The full graph is visible in `eri-pch_v2.dot` — outer loop included.

## Weaknesses

- More moving parts: streaming reducers, static argstream sizes, two-output
  iter_dispatch, fused input edges. More TTG idioms to know.
- `PivotSlab` is on the order of `(npairs_sp × npairs_pivot_sp)` doubles
  per slab; one full set is in flight per iteration. For water it's 4–8 KB
  per slab × 78 slabs = ~50 KB, but for large basis sets this scales.
  Could be reduced by sending only sparse contributions.
- The reducer must take `(Acc&, const In&)` and copies, because parsec's
  reducer doesn't move-from input.

## Differences from v1 at a glance

| Aspect                            | v1                              | v2                                  |
|-----------------------------------|---------------------------------|-------------------------------------|
| Outer iteration loop              | C++ `while`                     | feedback edge in TTG                |
| Phases per iteration              | invoke + fence (×2 typically)   | one inflight at a time              |
| Q row-block transport             | shared `CholeskyDriver::Q`      | `PivotSlab` value on edge           |
| Pivot shell-pair index            | metadata (`cur_pivot_sp`)       | edge value to compute_slab; field on slab |
| Cross-iteration synchronization   | `ttg::fence()`                  | streaming reducer + dependence edge |
| Output terminals on dispatch task | n/a (fan-out only)              | two: `out<0>` continue, `out<1>` terminate |
| Number of TTs                     | 4                               | 7                                   |

## Build & run

```sh
cmake --build . --target eri-pch_v2-parsec
./examples/eri-pch_v2-parsec [molecule.xyz] [basis] [tol]
```

Side effects: writes `eri-pch_v2.dot`.

## Reference numbers (water, single rank)

Numerically identical to v1 — verified on sto-3g/cc-pVDZ/def2-svp at
tol = 1e-8 and 1e-10. (See `eri-pch_v1.md` for the table.) Wall time on a
single rank is essentially the same as v1: TTG fence-cost between iterations
is the same order of magnitude as task spawn cost. v2 should win at scale
and on multi-rank runs where the fence is genuinely expensive, but the
fundamental sequential dependence chain (each iter needs d[] from the
previous iter's sub-decomp) limits how much overlap is achievable without
algorithmic changes.
