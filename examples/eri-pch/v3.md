# eri-pch_v3 — block update per shell pair (BLAS-3 gather)

Same TTG dataflow topology as `eri-pch_v2` (single connected graph with a
feedback edge, streaming reducers for diag init and the per-iter gather),
but the **inner sub-decomposition in `gather_pivot`** is replaced by a single
**block update** that produces all `W'` new Cholesky vectors of the
iteration's pivot shell pair `(A,B)` in one BLAS-3 sweep. The L matrix is
stored as a contiguous `Eigen::MatrixXd (P × M_capacity)` so dgemm/dtrsm
dispatch directly via Eigen's matrix operations.

## Why this exists

`v2` profiling on benzene/def2-svp showed:

```
compute_slab    :  5246 ms over 479655 calls on 12 threads     ← parallel; OK
gather subdecomp: 25057 ms over 1568 sub-pivots               ← all single-threaded
                                                                wall ≈ 24 s
```

i.e. the sub-pivot loop dominated wall, integral parallelism barely showed
up. The structural cause: `v2`'s gather chooses one sub-pivot at a time,
calls `apply_cholesky_update`, and that update's inner loop walks
`vector<vector<double>>` rows of L — pointer-chasing, no BLAS, single core.

The granularities of the algorithm don't actually match in `v2`:
- integrals are computed a *shell-pair block* at a time (W columns of M),
- but Cholesky vectors are produced *one column at a time*.

The W columns of the Q row block share the same prior-L contributions, so
all W' new Cholesky vectors that come out of one shell pair can be produced
together with a small W×W pivoted Cholesky of the residual + a single
`P×W' ← P×M_old · M_old×W'` dgemm + a `W'×W'` dtrsm. That's `v3`.

## Block update math

Inside `gather_pivot` for one iteration with pivot shell pair `(A,B)` and
slab-assembled `Q (P × W)`:

1. **Form residual**
   ```
   R_AB = Q[(A,B), :] − L[(A,B), :M_old] · L[(A,B), :M_old]^T        (W × W)
   ```
   Symmetrized to clean up round-off:
   ```
   R_AB := (R_AB + R_AB^T) / 2
   ```

2. **Pivoted Cholesky of R_AB** (small, W ≤ ~21 in practice) → permutation
   `Π` and lower-triangular factor `U (W' × W')` such that
   `R_AB[Π, Π] = U · U^T`. Stop when residual diagonal ≤ `X_max·1e−3` or
   `< tol`.

   Subtle bug to avoid: when swapping `perm[k] ↔ perm[best]` you must also
   swap the partially-computed `U.row(k).head(k) ↔ U.row(best).head(k)` so
   that subsequent `U[i, m]·U[k, m]` dot products reference the right rows.
   `v3`'s implementation does this; without the row swap, multi-column
   shell-pair iterations corrupt the factorization.

3. **Off-diagonal residual** (single dgemm, `P × W'`)
   ```
   residual = Q[:, Π] − L[:, :M_old] · L[(A,B), :M_old]^T[Π, :]
   ```

4. **Triangular solve** (single dtrsm, `W' × W'` triangular against
   `P × W'`)
   ```
   L_new = residual · U^{−T}
   ```
   so `L_new` (P × W') has columns laid out so that `L_new[(A,B)[Π[j]], k] =
   U[k, j]` for `k ≤ j` and the off-diagonal entries follow the standard
   Cholesky relation.

5. **Append** `L_new` to L's column buffer; update `M_current += W'`.
6. **Diagonal update**: `d -= rowwise_sum(L_new ⊙ L_new)`; clamp to ≥ 0.

The whole thing is one BLAS-3 dgemm, one dtrsm, plus the W×W pivoted
Cholesky (cheap). Each outer iteration is now a constant number of dense
linear-algebra calls instead of W single-column updates.

## Storage change

`v3` stores L as `Eigen::MatrixXd L (P × M_capacity)`, doubling capacity
on demand via `conservativeResize`. Initial capacity 64; for a final rank
of 1568 the resize cadence is at 64 → 128 → 256 → 512 → 1024 → 2048,
six resizes total. The total cost of resizes is bounded by `O(P · M_final)`
(geometric series), which on benzene is ~80 MB of total copies — trivial.

`d[]` becomes `Eigen::VectorXd` for cwise updates (`d -= L_new.cwiseAbs2().rowwise().sum()`).

## What stayed the same

- TTG topology: `drive_diag → compute_diag → diag_barrier → iter_dispatch
  ⇄ compute_slab → gather_pivot → terminate` with `fuse(e_seed_iter,
  e_loop_iter)` at iter_dispatch's input.
- Streaming reducers (sum-of-tokens for diag, concat-of-PivotSlabs for
  gather), `set_static_argstream_size(nshell_pairs)`.
- `PivotSlab` with templated `serialize()` for parsec.
- Per-thread libint engine cache.

## Wall-time / scaling

```
benzene / def2-svp / 12 cores
                          v2          v3
elapsed                   24 s        3.1 s        ~8x
user-time                 22.8 s      4.3 s
sys-time                   4.6 s      1.4 s
gather (subdecomp/block)  25 s        2.1 s        ~12x  ← BLAS-3 win
compute_slab CPU           5.2 s      5.7 s        same  (integral kernels unchanged)
involuntary cs            1.3 M       (low)        no more lock-contended single-thread loop
```

The gather went from "25 s of pointer-chasing single-thread loop" to
"2.1 s of BLAS-3", a ~12× speedup that comes entirely from running the
inner kernel as `noalias() * transpose` and `triangularView<Lower>().solveInPlace`.

## What's now the bottleneck (and natural v4 directions)

Now `compute_slab` and the gather are roughly the same wall-time order.
With the gather no longer dominating, the limiting factor per iteration is
`max(integral_compute_wall, gather_wall) ≈ 6.5 ms/iter`, set by gather (the
12-thread integral compute could finish in ~1.5 ms/iter if the gather
weren't blocking).

Things you'd try next:

- **Multi-threaded BLAS in the gather step.** Eigen will use a threaded
  BLAS automatically if linked. The `dgemm` is `P × M_old · M_old × W'`,
  ~50 M ops/iter — well-shaped for ~12× threaded BLAS speedup.
- **Pipelining iter N+1 over iter N's gather.** The next pivot depends on
  `d[]` which only gather updates, so this is structurally hard without
  speculation.
- **Coarsen `compute_slab` granularity.** 480 K tasks × ~12 µs is a lot of
  task-spawn pressure; bundling adjacent shell pairs into a single task
  would shrink that overhead further.

## Build & run

```sh
ninja -C cmake-build-relwithdebinfo eri-pch_v3-parsec
./examples/eri-pch_v3-parsec [molecule.xyz] [basis] [tol]
```

Side effects: writes `eri-pch_v3.dot`. Set `TTG_ERI_PCH_TRACE=1` to log
per-iteration block updates (`+W' from sp=...`).
