# eri-pch_v4 — row-parallel gather

Same TTG topology as v3, but the gather phase is split into a small
**setup** task (Q assembly + R_AB + pivoted Cholesky on the W×W block +
L_AB_chosen extraction, all cheap) and **N_CHUNKS** row-parallel
**chunk** tasks that each handle a disjoint row range of L.

The chunk does the only expensive piece: the BLAS-3 part of the block
update —

```text
L_new[p_lo:p_hi, :]  ←  ( Q_chosen[p_lo:p_hi, :]
                        − L[p_lo:p_hi, :M_old] · L_AB_chosen^T )
                        · U^{-T}
d[p_lo:p_hi]         ← d[p_lo:p_hi] − rowwise_sum(L_new ⊙ L_new)
```

Each chunk owns a disjoint row range of L and d, so writes don't conflict.
A streaming reducer (`set_static_argstream_size(N_CHUNKS)`) waits for all
chunks of iteration N before firing iteration N+1 onto the feedback edge.

## Topology change vs v3

```
v3:   gather_pivot ────────────────► e_loop_iter
                  (does setup + BIG block update + emit iter+1, all serial)

v4:   gather_pivot ─► e_chunk_dispatch ─► compute_l_chunk ×N_CHUNKS
                                                       │
                                                       ▼
                                              e_chunk_done (streaming)
                                                       │
                                                       ▼
                                              gather_finalize ─► e_loop_iter
```

`gather_pivot` keeps the streaming reducer over `PivotSlabs` and adds two
output terminals:
- `out<0> e_chunk_dispatch` — fans out N_CHUNKS chunks per iter (when
  W' > 0).
- `out<1> e_loop_iter` — direct iter+1 emission for the W' = 0 fast path
  (when the residual block decomposes to nothing this iteration).

`compute_l_chunk` takes `MultiIndex<2>{iter, c_idx}` and reads the
per-iter setup state from `drv.cur_block` (metadata). The streaming
barrier at `gather_finalize` ensures setup state isn't overwritten until
all chunks of that iteration are done.

`N_CHUNKS` defaults to `min(hardware_concurrency(), 24)` and can be
overridden via the env var `TTG_ERI_PCH_CHUNKS`.

## Two build variants

`eri-pch_v4` (default) compiles **without** `EIGEN_USE_BLAS`. Each
chunk's dgemm runs through Eigen's templated implementation, single-
threaded inside the call. Chunks parallelize cleanly under TTG.

`eri-pch_v4_blas` compiles **with** `EIGEN_USE_BLAS` and links the
system BLAS. On Linux with single-threaded OpenBLAS or MKL this usually
wins, because each call gets full BLAS throughput on its core. On macOS
with Apple Accelerate it can be **slower** than the no-BLAS build —
Accelerate's internal libdispatch threading saturates when called
concurrently from many worker threads (see "Pitfall" below).

## Performance — hexane (C6H14) / def2-tzvp / 12 cores

`N = 270`, `P = 36 585`, `nshell_pairs = 7 503`, `final rank = 3 438`,
`591 outer iterations`.

```
                     wall   user   chunk_compute   gather/iter   eff cores
v3 native eigen      38.3 s 55.1 s ─               55 ms (ser)   2.0
v3 + Accelerate      24.2 s 49.6 s ─               31 ms (ser)   2.9
v4 (BLAS, 12 ch)     24.7 s 181.7s 196 s CPU       28 ms/chunk   8.4 *
v4 native, 1 chunk   38.5 s ─      32.7 s CPU      55 ms wall    same as v3
v4 native, 4 chunks  16.8 s ─      42.8 s CPU      14 ms wall    ~5x
v4 native, 8 chunks  14.2 s ─      58.8 s CPU      11 ms wall    ~6x
v4 native, 12 chunks 14.3 s 87.8 s 77.7 s CPU      10 ms wall    7.9
v4 native, 24 chunks 13.1 s ─      72.6 s CPU       8 ms wall    ~6
```

`*` v4+BLAS on Apple Silicon: high CPU but no wall improvement — see Pitfall.

Key wins:
- **v4 native (12 chunks): 14.3 s wall** vs v3 native 38.3 s = **2.7× wall**
- **v4 native (24 chunks): 13.1 s wall**, near-saturation for this system
- Effective parallelism climbs from 2 cores (v3 native) to ~7–8 cores (v4)

## Pitfall: BLAS that internally threads via libdispatch

On macOS, `-framework Accelerate` routes Eigen's matrix-matrix products
through a libdispatch-backed thread pool. When a single thread calls
dgemm, Accelerate happily uses several cores and the v3 algorithm
(which has one big serial dgemm per iter) gets a clean speedup.

When **N_CHUNKS** TTG worker threads each call into Accelerate
simultaneously, all those calls funnel into the same libdispatch
queue and start serializing. Per-call latency stays roughly constant
regardless of chunk size — chunk size 1/12-th doesn't get 12× faster,
it gets ~1× faster:

| chunk size | v4 + Accelerate per-chunk | v4 native per-chunk |
|------------|---------------------------|---------------------|
| full P     | 31 ms                     | 55 ms               |
| P / 4      | 28 ms                     | 14 ms               |
| P / 12     | 28 ms                     | 10 ms               |
| P / 24     | 28 ms                     | 8 ms                |

`VECLIB_MAXIMUM_THREADS=1` does **not** fix this. The Accelerate
serialization is structural. On Linux with OpenBLAS or MKL, setting
`OPENBLAS_NUM_THREADS=1` (or `MKL_NUM_THREADS=1`) usually does keep
each call single-threaded, in which case v4_blas should beat v4 native.

So: on Apple Silicon, **use `eri-pch_v4` (no BLAS)**. On Linux with a
proper BLAS plus `*_NUM_THREADS=1`, **try `eri-pch_v4_blas`**.

## What's now the bottleneck

With chunks at N=12, the per-iter wall breakdown is roughly:
- iter_dispatch ~3 ms (sequential, ~7 500 sendk's)
- compute_slab parallel wall ~7 ms (12-thread integral compute)
- gather setup ~0.5 ms
- chunk compute parallel wall ~10 ms (memory-bandwidth-bound dgemm)
- gather_finalize ~negligible

So per iter ≈ 20 ms × 591 iters ≈ 12 s + a couple s of synchronization
overhead → 14 s observed. Two natural directions for v5:

1. **Coarsen `compute_slab`** — 4.4 M tasks at ~10 µs each is borderline
   wasteful. Bundling several shell pairs per task drops the spawn cost
   and could shave most of compute_slab's wall.
2. **Pipeline iter N+1's compute_slab over iter N's chunk compute.**
   Currently the feedback edge serializes them. The next pivot depends
   on `d[]` (only chunks update), but compute_slab for sp ≠ pivot_sp(N)
   doesn't actually need d updates from iter N — it just needs a pivot
   shell pair. Speculative or partial pipelining could overlap them.
3. **Reduce memory traffic in the chunk dgemm.** Each chunk reads
   `L[p_lo:p_hi, :M_old]` (M_old growing to ~3 500). For large systems
   this is bandwidth-limited; periodic re-decomposition or a more
   cache-friendly layout could help.

## Build & run

```sh
ninja -C cmake-build-relwithdebinfo eri-pch_v4-parsec
./examples/eri-pch_v4-parsec [molecule.xyz] [basis] [tol]
TTG_ERI_PCH_CHUNKS=24 ./examples/eri-pch_v4-parsec ~/tmp/C6H14.xyz def2-tzvp
```

Side effects: writes `eri-pch_v4.dot`. `TTG_ERI_PCH_CHUNKS=N` overrides
the chunk count; `TTG_ERI_PCH_TRACE=1` logs per-iter block updates.
