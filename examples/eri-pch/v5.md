# eri-pch_v5 — data on the flow

v1..v4 encode the algorithm as a *control-flow* TTG: the per-iteration
state (`d[]`, `L[]`) lives as members of `CholeskyDriver`, and tasks
read or update them by reference. That works in shared memory but rules
out distributed execution — a TT running on rank `r` can't follow a
reference into rank 0's process memory.

v5 makes the per-iteration data flow on edges. Concretely:

- Per row-chunk `L` is a **bag of per-iter tiles**, flowing iter to iter
  on `e_L_tile_in(iter, chunk)`:
  ```cpp
  using LStack = std::vector<TensorTile<2>>;  // each tile: (P_chunk, Wp_iter)
  ```
  Each successful iter appends one new `(P_chunk × Wp)` tile (typically
  24-150 KB) instead of allocating a fresh `(P_chunk × M_new)` matrix
  and memcpy'ing the previous tile into its left columns. The bag
  stays on chunk `c`'s home rank for the entire run (chunks are pinned
  by keymap to `c % nranks`); only the drain pass ships it across
  ranks, once.
- `e_d_tile_in(iter, chunk)` carries a single `Eigen::Tensor<double, 1>`
  of shape `(P_chunk,)`.
- Cross-rank payloads — `IterSetup::L_AB_chosen` and
  `LABContribution::rows` — are **single contiguous matrices**
  (`Wp × M_old` and `n_rows × M_old` respectively), packed
  left-to-right in the same column-block order as the L bag. The
  block-Cholesky update
  ```
  L_new = Q_chunk - sum_k L_in[k] · L_AB_chosen[col_off_k, Wp_k]^T
  ```
  walks the bag with column offsets that match each tile's `Wp_k`, so
  the multi-GEMM has the same FLOPs as v4's monolithic dgemm but
  needs neither a monolithic `L_in` on the chunk side nor a
  list-of-blocks on the wire.
- Global argmax is a streaming reduction over per-chunk argmax items.

`TensorTile<Rank, StorageOrder>` is a thin wrapper around an
`Eigen::Tensor<double, Rank, StorageOrder>` with the
`serialize(ar, version)` and `serialize(ar)` methods TTG looks for
(boost-style and madness-style respectively). Numerical kernels operate
via `Eigen::Map<MatrixT>` views over the tensor storage, where `MatrixT`
matches the storage order — so BLAS-3 paths remain intact and there's
no permute when interfacing with row-major external buffers.

## Topology

```
drive_diag → compute_diag ⇒ init_phase  →  e_L_tile_in
                                       →  e_d_tile_in
                                       →  e_argmax_in (stream × Nc)
                              ↓
                       argmax_reducer  →  iter_dispatch
                                                ├─ continue → compute_slab × nsp
                                                │            → gather_pivot ⇐ stream
                                                │            ↑          stream
                                                │       L_AB_extract × Nc
                                                │            ↑
                                                │     (consumes L_tile)
                                                │   gather_pivot → e_setup, e_q_chunk
                                                │                       ↓
                                                │                compute_l_chunk × Nc
                                                │                       ↓
                                                │              (L_tile, d_tile, argmax) → loop
                                                └─ terminate + drain → terminate
                                                                  ↓
                                                            (drain pass consumes
                                                             stale L_tile/d_tile
                                                             so fence returns)
```

`compute_l_chunk` reads `(L_tile, d_tile, Q_chunk, IterSetup)` at
`(iter, chunk)` and emits `(L_tile, d_tile, argmax_item)` at
`(iter+1, chunk)`. The full state of an in-progress decomposition is
therefore the set of in-flight tile values on the loopback edges.

## Drain pass

The interesting wrinkle is termination. When `iter_dispatch` decides
the iteration is converged (global `X_max < tol`), `compute_l_chunk`
of the previous iteration has already broadcast `L_tile`, `d_tile`,
and an `argmax_item` for the now-converged iter. Those values are
*orphan*: their consumers (`L_AB_extract` and `compute_l_chunk` for
the same iter) need a `DispatchInfo` and an `IterSetup` that
`iter_dispatch` won't emit.

Without intervention, parsec keeps the partially-fed tasks pending
forever and `ttg::fence()` doesn't return.

v5 handles this with an explicit drain. `DispatchInfo`, `PivotSlab`,
and `IterSetup` each carry a `terminate` flag. On convergence,
`iter_dispatch` fires both `e_terminate` *and* a fan-out of
`DispatchInfo{terminate=true}` to `compute_slab` and `L_AB_extract`.
Each downstream task short-circuits (no integrals, no row extract),
emits a marker, and gets reduced. `gather_pivot` recognizes the marker
and broadcasts `IterSetup{terminate=true}` plus a zero-column
`Q_chunk` to every chunk. `compute_l_chunk` then has all four inputs
and ships its L bag to `collect_final_L` (pinned to rank 0) on the
new `e_final_L` edge instead of writing to `drv.final_L_bags`
directly. The graph quiesces, the fence returns, and rank 0's driver
has every chunk's final L bag ready for repack.

## Distribution across MPI ranks

v5 is the first variant whose data flows on edges, and so the first
that can run distributed. Keymaps split the graph into a control
plane on rank 0 and a data plane that scales out by chunk:

| Task              | Keymap                         | Why                                                        |
|-------------------|--------------------------------|------------------------------------------------------------|
| `diag_compute`    | rank 0                         | writes `drv.d_init` directly (legacy side-effect path)     |
| `init_phase`      | rank 0                         | reads `drv.d_init`                                         |
| `iter_dispatch`   | rank 0                         | writes `drv.total_iters` (stat counter)                    |
| `argmax_reducer`  | rank 0                         | needs a single accumulator, broadcasts result              |
| `compute_slab`    | `sp_idx % nranks`              | integral compute parallelizes across nodes                 |
| `gather_pivot`    | rank 0                         | writes `drv.total_new_columns`; small per-iter centroid    |
| `L_AB_extract`    | `chunk % nranks`               | reads the chunk's L bag locally — no cross-rank ship       |
| `compute_l_chunk` | `chunk % nranks`               | the L bag stays on its home rank for the entire run        |
| `collect_final_L` | rank 0                         | drain pass ships each chunk's bag here for the global L    |
| `terminate`       | rank 0                         | only rank 0 prints; needs the right counters               |

The L bag for chunk `c` is therefore created, updated, and consumed
on rank `c % nranks` for the entire run; only at termination does it
ship to rank 0 (one MPI send per chunk, once). Q assembly and the
`R_AB`/`L_AB`-residual reductions live on rank 0 (control plane).

Validated: 1, 2, 4 ranks on water/sto-3g, water/def2-svp, and 2
ranks on water/def2-tzvp (all match single-rank ranks and residuals
to ~1e-16). At larger problem sizes (e.g. benzene/def2-svp at 2
ranks) parsec's MPI layer raises `MPI_ERR_TRUNCATE` after the
algorithm completes — likely a buffer-size limit on serialized
`vector<TensorTile<2>>` payloads in the per-iter `IterSetup`. A v6
follow-up that periodically compacts the bag (or splits the
`L_AB_chosen_blocks` ship) should remove that limit.

## Layout: row-major slab, column-major everything else

`common::compute_pivot_block` writes its `(npairs, W)`
integral block in **row-major** layout (`buf[i * W + j]`). v1..v4 read
that buffer as a flat `std::vector<double>` with the matching index
formula, so they see the right values. The first cut of v5 stored the
slab in a column-major `TensorTile<2>` and read it with `as_matrix()`
— a `Map<MatrixXd>` view that interprets the same bytes in
column-major order. For `npairs ≠ W` the resulting `Q` matrix was
effectively transposed-with-rebroadcast, and only the AB sub-block of
the very first iter happened to look correct. Subsequent iters
silently over-subtracted at non-AB rows, sending many `d[p]` to zero
too early and yielding rank-deficient `L`.

The fix is to make `TensorTile` parametric in storage order:

```cpp
template <int Rank, int StorageOrder = Eigen::ColMajor>
struct TensorTile { ... };
```

`as_matrix()` returns an `Eigen::Map<MatrixT>` whose layout matches the
underlying tensor, so reads and writes go through the same indexing.
`PivotSlab::rows` is `TensorTile<2, Eigen::RowMajor>`, which lines up
exactly with the kernel's `buf[i*W+j]` layout — the integral engine
writes directly into the tile, no temp buffer or permute. Everything
else (L tiles, d tiles, Q_chunk, U_block, L_AB_chosen) stays
column-major where Eigen's BLAS-3 paths and `solveInPlace` are
fastest.

## Performance vs v4 (12 cores, parsec, Apple Silicon)

| System          | v4 wall | v5 wall | v5 user | v5 sys |
|-----------------|---------|---------|---------|--------|
| benzene/def2-svp|  1.4 s  |  1.3 s  |  5.9 s  |  3.8 s |
| hexane/def2-tzvp| 14.1 s  | 15.0 s  | 91.2 s  | 34.9 s |

v5 essentially matches v4 on benzene/svp and is within ~6% on
hexane/tzvp. The bag keeps allocation traffic small (no per-iter
`mmap` hits); the packed L_AB_chosen / LABContribution matrices
keep cross-rank payloads to a single tile each, with no
`vector<TensorTile<2>>` on the wire.

## Build & run

```sh
ninja -C cmake-build-relwithdebinfo eri-pch_v5-parsec
./examples/eri-pch_v5-parsec [molecule.xyz] [basis] [tol]
TTG_ERI_PCH_CHUNKS=24 ./examples/eri-pch_v5-parsec ~/tmp/C6H14.xyz def2-tzvp

# multi-rank
mpirun -n 2 ./examples/eri-pch_v5-parsec '' def2-svp
mpirun -n 4 ./examples/eri-pch_v5-parsec '' sto-3g
```

Side effects: writes `eri-pch_v5.dot`. `TTG_ERI_PCH_CHUNKS=N`
overrides the chunk count; `TTG_ERI_PCH_TRACE=1` prints per-iter
block updates.

## Caveats

- Two consumers read `e_L_tile_in` (`L_AB_extract` and
  `compute_l_chunk`), so each iter the bag is deep-copied to both. With
  shared-pointer-backed tiles the second copy could be a refcount bump;
  a follow-up.
- Many small per-iter dgemms in the multi-GEMM step (`Wp_k` is often
  1-3). FLOP count is identical to v4's monolithic dgemm but BLAS-3
  efficiency is a bit lower; periodic compaction (fold the last N
  bag entries into one tile) would close the gap.
- `diag_compute` is currently pinned to rank 0 because it writes
  `drv.d_init` via shared-memory side-effects. A v6 should have it
  emit its slice on an edge so that integral compute parallelizes
  across nodes from iter 0.
- Distributed runs at large problem size (e.g. benzene/def2-svp at
  2 ranks on the local test box) still hit `MPI_ERR_TRUNCATE` after
  the algorithm completes. The per-iter cross-rank payloads are now
  single-matrix (no `vector<TensorTile<2>>` on the wire), so the
  symptom is most likely in the streaming-reducer paths
  (`gather_pivot`'s `PivotSlabs` reducer fires once per iter with
  `nsp` per-shell-pair messages) — a parsec/MPI eager-protocol issue
  rather than an algorithm-level one.
- `CholeskyFlow` is built once per problem; rebuilding the graph is
  not yet free.
- The drain pass adds one extra `compute_slab × nsp` task fan-out per
  problem. Negligible at any non-trivial problem size, but visible in
  the profile for tiny tests.
